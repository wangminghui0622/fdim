# 已读回执修复说明

## 问题描述

根据错误日志分析，发现两个主要问题：

### 问题1：接收方读了消息，但发送方还是显示未读
当会话刚创建且没有消息时，系统会尝试发送已读回执，但 `hasReadSeq` 为 0。由于 protobuf 默认会省略零值字段，导致接收方无法正确解析已读回执通知。

### 问题2：进入聊天页面后，未读数字没有消失
前端进入聊天页面时调用了 `markConversationMessageAsRead`，但可能由于以下原因导致未读数没有清除：
- 会话刚创建时 `maxSeq = 0`，没有消息可标记
- ConversationID 不匹配（`si_` vs `n_` 前缀）
- 已读回执没有正确发送给发送方

### 错误日志示例
```json
{
  "@timestamp":"2026-03-19T00:33:22.544+08:00",
  "caller":"logic/markconversationasreadlogic.go:217",
  "content":"【ERROR】hasReadSeq is 0, this will be omitted by protobuf serialization!",
  "conversationID":"si_3221069968_5423720711",
  "level":"error"
}
```

## 根本原因分析

### 场景1：会话刚创建，没有消息
1. 用户A和用户B刚建立会话
2. 用户B进入聊天页面，前端调用 `markConversationMessageAsRead`
3. 此时 `maxSeq = 0`（没有消息）
4. 后端 `hasReadSeq = 0`
5. 代码仍然尝试发送已读回执通知
6. Protobuf 序列化时省略了 `hasReadSeq = 0` 字段
7. 用户A收到的通知中缺少 `hasReadSeq` 字段，无法更新消息状态

### 场景2：有消息但已读回执未生效
1. 用户A发送消息给用户B（seq=1）
2. 用户B进入聊天页面，调用 `markConversationMessageAsRead`
3. 后端自动填充 `hasReadSeq = maxSeq = 1`
4. 更新数据库中的 `hasReadSeq = 1`
5. 发送已读回执给用户A
6. 但用户A的前端可能没有正确处理该通知

## 解决方案

### 后端修复（已完成）

在 [`markconversationasreadlogic.go`](../rpc/msg/internal/logic/markconversationasreadlogic.go) 中：

#### 1. 避免发送无效的已读回执

**单聊场景**（第126-140行）：
```go
// 只有当 hasReadSeq > 0 或有具体的 seqs 时才发送（避免发送空的已读回执）
if hasReadSeq > 0 || len(seqs) > 0 {
    recvID := l.conversationAndGetRecvID(conversationResp.Conversation, req.UserID)
    l.Infow("Sending HasReadReceipt notification to sender",
        logx.Field("fromUserID", req.UserID),
        logx.Field("toUserID", recvID),
        logx.Field("seqs", seqs),
        logx.Field("hasReadSeq", hasReadSeq))
    l.sendMarkAsReadNotification(l.ctx, req.ConversationID, conversationResp.Conversation.ConversationType, req.UserID, recvID, seqs, hasReadSeq)
} else {
    l.Infow("Skipping HasReadReceipt notification (no messages to mark as read)",
        logx.Field("hasReadSeq", hasReadSeq),
        logx.Field("seqs", seqs))
}
```

**群聊场景**（第150-154行）：
```go
// 只有当 hasReadSeq > 0 时才发送通知
if hasReadSeq > 0 {
    l.sendMarkAsReadNotification(l.ctx, req.ConversationID, constant.SingleChatType, req.UserID, req.UserID, seqs, hasReadSeq)
}
```

#### 2. 增强日志输出

添加了更详细的日志，包括 `conversationID`，便于调试：
```go
l.Infow("Auto-filled hasReadSeq with maxSeq", 
    logx.Field("maxSeq", maxSeq),
    logx.Field("conversationID", req.ConversationID))
```

#### 3. 简化通知发送逻辑

移除了误导性的错误日志，简化了 `sendMarkAsReadNotification` 方法（第202-223行）。

### 前端检查点

前端代码看起来是正确的（[`chat_page.dart`](../../app/lib/pages/chat/chat_page.dart)）：

1. **第54行**：进入聊天页面时调用 `_markAsRead()`
2. **第106-129行**：正确监听已读回执 `_onReadReceipt`

## 可能的遗留问题

如果修复后问题仍然存在，需要检查：

### 1. ConversationID 不一致
- 消息使用 `si_3221069968_5423720711`
- 标记已读使用 `n_3221069968_5423720711`
- **解决方案**：确保前后端使用相同的 conversationID 生成规则

### 2. 前端未正确处理已读回执
- 检查 `c2cReadReceiptSubject` 是否正确触发
- 检查 `ReadReceiptInfo` 的解析是否正确
- **解决方案**：在前端添加更多日志，确认收到的数据结构

### 3. 消息的 seq 字段未正确设置
- 检查发送消息时是否正确设置了 `seq`
- 检查接收消息时 `seq` 是否正确解析
- **解决方案**：在消息发送和接收时添加日志，确认 `seq` 值

### 4. 会话未读数更新问题
- 后端发送了 `ConversationUnreadChangeNotification`（第175-176行）
- 前端是否正确监听并处理该通知
- **解决方案**：检查前端的 `conversationChangedSubject` 监听器
